# Track feature parity across platforms

Maintain a feature × platform parity table for Mist, recording shipped
capabilities, platform gaps, and planned work. Update it whenever a feature
lands or a platform adapter changes.

## Legend

- **Full** — usable end to end on that platform without manual workarounds.
- **Partial** — works, but requires a manual action or has a known limitation.
- **Missing** — not implemented on that platform.
- **N/A** — the platform cannot support it by policy or OS restriction.

## Verified on-device (Pixel 10 Pro ↔ Linux)

- Pairing via QR, then reconnect.
- Notification send Linux → Pixel and receive Pixel → Linux.
- Clipboard text both directions.
- Clipboard PNG both directions, byte-identical SHA-256.
- Android share sheet → Mist: text and a 438x904 JPEG both delivered to Linux
  and decoded cleanly.
- Queued delivery: disconnected the Pixel, sent `queued_while_offline` from
  Linux, and it auto-reconnected and arrived in the Pixel clipboard.
- Linux auto-watch: plain `wl-copy` on Linux synced text and a PNG to the Pixel
  with no explicit command, and Android share text landed back in the Wayland
  clipboard. Repeated polling showed no echo ping-pong.
- Android service survives activity close; boot receiver added but device
  restart not yet re-verified after the clipboard changes.

## Android clipboard auto-detect research (2026-11-07)

Android 10+ restricts clipboard reads to the focused app, the default IME, or
callers holding the system-only `READ_CLIPBOARD_IN_BACKGROUND` role permission.
There is no supported background clipboard API for ordinary apps.

### Accessibility services

Accessibility does **not** grant clipboard reads on stock AOSP/Pixel:

- `AccessibilityService` is not in the ClipboardService allow-list.
- Empirically on API 35, an accessibility service was denied with
  `ClipboardService: Denying clipboard access ... application is not in focus nor
  is it a system service`.
- Some OEM ROMs (Samsung/Xiaomi) reportedly allow accessibility capture, and
  some clipboard apps advertise it. Treat that as OEM-specific, undocumented
  behavior, not a platform guarantee.
- Accessibility can read on-screen text and perform `ACTION_PASTE` into a
  focused editable field. That simulates a paste; it is not a reliable
  background clipboard read.

### KDE Connect workarounds

KDE Connect still supports Android clipboard sync through privileged paths:

- `adb shell pm grant <pkg> android.permission.READ_LOGS` plus parsing clipboard
  events from `logcat`; needs `SYSTEM_ALERT_WINDOW` to stay responsive.
- Shizuku: run the same logcat monitor with shell (ADB) UID instead of asking
  for READ_LOGS. Some forks use a Shizuku user service that reads the clipboard
  directly with shell UID.
- Some guides use `appops set <pkg> READ_CLIPBOARD allow` + `SYSTEM_ALERT_WINDOW`.
  Not a public API and not reliable across builds.

### Shizuku

Open-source service by RikkaApps. It starts a privileged process with ADB shell
(or root) UID and proxies Binder calls from user-authorized apps, so an app can
use APIs normally reserved for shell.

Startup modes: root, USB ADB (one-off `start.sh`), or wireless debugging
(Android 11+). Wireless startup needs no computer, but the system requires Wi-Fi
to be enabled, and it must be repeated after each reboot.

Wireless startup is device-local: the manager app uses mDNS
(`_adb-tls-pairing._tcp`, `_adb-tls-connect._tcp`) to find adbd's ports, then
connects to `127.0.0.1` on those ports. A PC running `adb` connects to the
device's Wi-Fi IP instead; both talk to the same adbd TLS server, so the network
hop is loopback for Shizuku and over Wi-Fi for a PC.

Shell privileges are narrower than root and vary by Android version and OEM.
Authorizing an app grants it shell-level access, so only trusted APKs should be
allowed.

### Why logcat parsing is not viable

- Modern Android redacts clipboard content from logs (`ClipboardService` logs
  events and denials, not the payload). Log parsing cannot recover the content;
  it can only observe a change, which still requires a privileged read.
- Battery and CPU: a persistent logcat reader keeps the CPU awake and parses a
  high-volume buffer shared by every app.
- Privacy: reading all app logs is unacceptable for a clipboard bridge.

### Preferred Android paths

1. **Focused-app read** (implemented): the `Send clipboard` button reads while
   Mist is focused. No privileges.
2. **Share target** (recommended next): register `ACTION_SEND` for text and
   images so any app can share directly to Mist. Explicit intent, no clipboard
   read, no privileges, and it handles images properly via `ClipData`.
3. **Opt-in privileged adapter** (later): Shizuku/root auto-detect, clearly
   labelled, never required for normal operation.

### Decision

Keep explicit send as the Android baseline and add a share target next.
Auto-detect, if added later, is an explicit opt-in Shizuku/root adapter; never a
default, and never READ_LOGS.

## Immediate gaps to close

1. Linux clipboard watcher (`wl-clipboard-rs`) for automatic send.
2. Apply received clipboard content to the Linux native clipboard.
3. Per-device clipboard opt-in, separate from notification selection.
4. On-device verification of image receive on Android from Linux (partially
   proven) and boot restart after the latest build.
